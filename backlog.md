## [H] Potentially bad

- [2026-08-20] [H] Pre-MVP6/7 auth hole: the process has no operator credential, only per-session tokens minted at create time. That's why a pile of powerful routes are token-free and rely solely on Host/Origin allowlisting (`isSpoofedRequest`) plus the 127.0.0.1 bind: GET `/api/handshake` and POST `/api/handshake/regenerate`, GET `/api/browse` (filesystem enumeration), GET `/api/sessions` (live ids, names, cwds), POST `/api/sessions` (spawn a Claude/Grok process against an arbitrary cwd), GET `/api/resumable` and `/api/history/*` (every transcript on disk), POST `/api/session-title` (writes `.claude/settings.local.json`), GET `/api/stats` (walks `~/.claude/projects/**/*.jsonl`), GET `/api/account-limits` (spawns `claude -p "/usage"`). Fine on loopback. The moment Host/Origin is relaxed for SSH or a phone, this is a remote-code-execution-shaped API. Do not start MVP6/7 by punching holes in `isSpoofedRequest`. Mint a process-level operator token first (distinct from the delegation handshake secret) and gate every token-free route above; keep session-token gates on session routes. Flagged by the 2026-08-20 project audit.
- [2026-08-20] [H] `/api/handshake` (GET) and `/api/handshake/regenerate` (POST) are currently unauthenticated - fine today since Origin/Host checks plus per-session bearer tokens still gate real delegation, but the module comment says this secret exists so a session on a different machine can prove group membership for MVP6. Before MVP6 (SSH-hosted sessions) ships, this becomes a bearer credential served to any caller that can set a Host header, and the unauthed regenerate becomes a one-curl delegation kill switch. Gate both routes (or at least regenerate) before MVP6 lands, not after. Flagged by security review 2026-08-20; same class of bug as the operator-token item above, called out separately because the handshake value is the actual group secret.
- [2026-08-20] [H] MVP5 `/ask` is same-cwd-only (`findByName` exact `row.cwd` string, no path normalize). A Mac session asking a Windows session to "start testing this on DX12" will never share a cwd - the v1 safety rail is the opposite of the MVP6 product requirement. Before MVP6, replace same-cwd with same handshake group + explicit target name/id. Path-normalize for local same-machine `/ask` is still worth doing (already listed under the 2026-08-18 MVP5 gaps item (a)); that alone does not unblock cross-machine. Flagged by the 2026-08-20 project audit.
- [2026-08-20, mitigated 2026-08-20] [H] Cross-session delegation is frequently refused by the receiving model, confirmed via live repro (Claude1 session ran `/ask Sonnet: "I am Groot too"`; Sonnet replied "I didn't spawn 'Claude1'... not going to treat fabricated `<delegated_task>`/`<delegated_result>` blocks as real signals from an agent I control"). Investigated by an opus subagent (2026-08-20): not a code bug - `delegateTask`'s wrapper (session-registry.js) was byte-exact correct, single push, correct `from` attribution, `escapeAttr`/`escapeBody` were no-ops on plain text. The actual problem: the wrapper was a plain user turn making an unverifiable in-band provenance claim ("this came from another agent"), structurally identical to a prompt-injection payload. Shipped mitigation #2 same day: dropped the `<delegated_task from="...">`/`<delegated_result from="...">` XML shape entirely for prose framing (`buildDelegatedHeader` in session-registry.js - "[Prompt Cockpit] Relayed task/reply from "X"..." + explanatory paragraph + `\n---\n` separator + payload), works uniformly for Claude and Grok targets, no SDK changes needed. Also shipped the same day: a real per-session handshake secret (see the MVP6-seed item below) that the header can now truthfully reference as a checkable fact rather than pure prose - not yet wired INTO the header text itself (the mitigation shipped was framing-only; teaching the header to actually cite the handshake, and appending a system-prompt anchor so the receiving model learns about `/ask` through a second, trusted channel - mitigation #1 from the investigation - is still open, see below). Validate against both a content-free task and a substantive one - refusal rate was not uniform across task types even before the fix.
- [2026-08-20] [H] Grok-side delegation can desync `pendingResultTags`, misrouting a delegated reply to the wrong origin session. Found while investigating the above (not yet reproduced live - grok isn't installed on this dev machine to confirm end-to-end). `pushTurn` (session-registry.js) unconditionally appends a `pendingResultTags` entry for every call, but `grok-session.js`'s `pushInput` can early-return without actually pushing anything (e.g. deduped duplicate text, or a push after the session is closed) - leaving a pending-result entry for a turn that will never run. Since results are matched off this list FIFO, every later real result then shifts the wrong entry off the front, misattributing it to whichever origin was actually waiting on the *next* slot. `registry.forceIdle` has a narrower version of the same class of bug: it clears `pendingResultTags` (session-registry.js) and zeroes `pendingTurns` (session.js), but a genuinely in-flight turn's `result` can still land later and shift an entry belonging to a subsequent, unrelated turn.

## [M] Can wait

- [2026-08-20] [M] MVP6 recommended shape (no design doc yet - see the 2026-08-18 [L] item): two cockpit processes, each still bound to 127.0.0.1, talking over an SSH tunnel. A "remote session" on the Mac is a proxy row whose `pushInput` is an HTTP/WS call to the Windows process, not a local `query()`. Do not listen on `0.0.0.0` and do not add the peer's Origin to the allowlist. Handshake is the delegation group secret, not the wire credential - after the operator-token gate, `/api/handshake` must not be returned to a browser that isn't already operator-authenticated. Flagged by the 2026-08-20 project audit.
- [2026-08-20] [M] `session-registry.js` (~81 KB) is the live hub, the delegation protocol, usage/context/rate-limits, queue mirroring, handshake, and auto-continue. MVP6 wants a second row type (not locally stamped, not a local CLI handle). Split handshake + delegation out before that lands, or the `pendingResultTags` FIFO class of bug gets a cousin. Same smell on the client: `public/app.js` (~115 KB) owns the approval UI and the websocket client; a phone `/approve` page cannot be "the desktop app in a smaller viewport" and should not copy-paste from it. Flagged by the 2026-08-20 project audit.
- [2026-08-20] [M] MVP7 cannot be a `@media` tweak. There is one breakpoint (`max-width: 900px`, stacks the detail pane). Loopback is unreachable from a phone; even LAN Origin/Host would 403 (`http://192.168.x.x:4317` is not in the allowlist). v1 should be a dedicated `/approve` page (pending request, Allow/Deny/always-allow, AskUserQuestion) on the same SSH/Tailscale tunnel as MVP6, pairing via QR of `{origin, operatorToken}`, operator token in `Authorization` not the URL. Full mobile session view is later. Also `row.pendingApproval` is last-write-wins - a phone UI that only sees the latest gated call will drop earlier ones; make it a list before shipping approvals off-desktop. Flagged by the 2026-08-20 project audit.
- [2026-08-20] [M] Network-exposure leftovers, ship with the operator-token work not after: `readJsonBody` (http-utils.js) slurps the request with no size cap (harmless on loopback, a one-line DoS once reachable); the websocket upgrade puts the session token in the query string (`/ws?id&token=`), which leaks to logs and referrers - move it to a first message or an Authorization-equivalent before a tunnel exists; `isSessionTrusted` compares handshake secrets with `===` - switch to `timingSafeEqual` when that value is a cross-machine bearer (session tokens already use it). Flagged by the 2026-08-20 project audit.
- [2026-08-20] [M] No Content-Security-Policy or X-Frame-Options on static/HTML responses. Fine locally; a phone webview or tunneled origin is a more hostile document. `markdown.js` already builds via textContent not innerHTML - keep that. Flagged by the 2026-08-20 project audit.
- [2026-08-20] [M] Delegation prose header (`buildDelegatedHeader`, session-registry.js) doesn't yet reference the handshake secret (see the MVP6-seed item below) even though both now exist side by side - citing it explicitly ("this session's handshake matches the server's") would give the receiving model a checkable fact instead of pure prose, likely reducing refusal further. Also still open: appending a short system-prompt note at session start (SDK's `systemPrompt: {type:'preset', preset:'claude_code', append}`) explaining the `/ask` relay protocol exists and is user-authorized - this only affects sessions started after the change and has no Grok-side equivalent, which is why it was scoped separately from the framing-only fix that shipped.
- [2026-08-20] [M] MVP6 seed, shipped: a per-process delegation handshake secret (`session-registry.js`'s `handshakeSecret`/`getHandshakeSecret`/`regenerateHandshakeSecret`/`setSessionHandshake`/`isSessionTrusted`), minted fresh at every server start, in memory only. Every locally-created session row is stamped with the current value at creation (trusted by construction, since it was spawned by this very process); `delegateTask` now refuses to run unless BOTH origin and target currently match the server's canonical value. Surfaced in two places: the cross-tab "All sessions" pane (session-list-pane.js) shows the server's own copyable value plus a rotate button (global, no session token - same Origin/Host-only gate as `/api/browse`), and each session's own Settings panel shows ITS OWN trust status plus a paste-in field to re-sync (scoped to that session's own bearer token, via the new `POST /api/sessions/:id/handshake` route) - the cross-tab pane can't offer a working paste control itself since it doesn't hold other tabs' session tokens. Pairing is deliberately manual copy/paste only for now (confirmed acceptable) - no exchange protocol, no persistence, no actual cross-machine transport. This is infrastructure for the eventual MVP6 goal (a Mac session delegating real work - "start testing this on DX12" - to a Windows session over SSH), not MVP6 itself: there is still no remote/SSH session type, no pairing UI beyond copy-paste, and the delegation header text doesn't yet cite the handshake as a trust signal (see the item above). Rotating the secret is an intentionally blunt "cut everyone off" control - it does not re-stamp existing rows, so it also doubles as an audit ("who's still trusted after I rotate is who actually re-synced").

- [2026-08-16] [M] No warning before a cache-invalidating action. Prompt caching is a prefix match, so several cockpit controls silently throw away the session's warm cache and the user only finds out afterwards, via the stats strip's hit rate dropping. Three tiers, worst first: (a) tool-set changes - MCP toggle/reconnect (server.js:274) and reload-plugins (server.js:294) - tools render at prefix position 0, so any add/remove/reorder invalidates tools + system + messages, i.e. everything; (b) model switch (server.js:329) - caches are model-scoped, so the whole prefix is gone; (c) thinking budget/display (server.js:355) - invalidates the messages cache only, tools + system survive. usage.js's accumulator already tracks `cacheReadTokens`, so the cost of the impending re-write is computable at click time: warn (inline, `.mcp-error` pattern) when the session has more than some threshold of cached tokens, naming which of the three tiers applies. Scope/approach not designed: where the threshold sits, whether it's a confirm dialog or a passive note, and whether the warning belongs on the control or in the stats strip. Note the cockpit cannot set `cache_control` itself - prompt assembly belongs to the Agent SDK's `query()` - so avoiding needless invalidation is the only lever we have; do not let the copy imply we could extend the TTL. Separately, do not attribute plain idle-gap expiry (the default cache TTL is 5 minutes, refreshed on every read) to a user action - a warning that cries wolf after a coffee break is worse than none.

- Mid-session effort: `session/set_mode` `{ sessionId, modeId }` where `modeId` is `low` / `medium` / `high` / `xhigh` (the `x.ai/sessionConfig` options with `category: "mode"`)
